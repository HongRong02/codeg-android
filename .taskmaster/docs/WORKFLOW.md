# 开发流程：批次 → 层级 → 集成 → 测试 → 修复 → 发布

> 协调方（Claude）的完整流程。任务方（Codex）只需读 `CONVENTIONS.md`，本页不必读。
> 任务关系图在 `.taskmaster/docs/graphs/<批次>.md`，任务文档模板 `tasks/TEMPLATE.md`，测试文档模板 `tests/TEMPLATE.md`，bug 单模板 `bugs/TEMPLATE.md`。

## 0. 分支模型

```
main ─────────────────────────────●──────────── 发版（push main = Release）
  │                               ↑ 第 7 步：批次全部通过后合入
  └─ sit（集成分支，长期）─●──●──●──●──●──●──●
        ↑ 合入 task/*   ↑ 合入 fix/*      ↑ 定期 merge main（热修复同步）
     task/Txx-<短名>    fix/Bnn-<区域>
     （基于派发时的 sit）（基于最新 sit）
```

- `main`：只接收 `sit` 的整批合入和紧急热修复。push main（非文档改动）即发版。
- `sit`：所有开发和修复的集成点，CI 与真机测试都在这里做。除了"合并冲突解决"和"code-index 重新生成"，**不在 sit 上直接写业务代码**。
- `task/Txx-<短名>`：开发任务分支，基于派发时的 sit。
- `fix/Bnn-<区域>`：修复任务分支，基于最新的 sit。
- `hotfix/<短名>`：线上紧急修复，基于 main → 合入 main 发版 → 立刻 `merge main → sit`。

**问题归属边界（核心规则）**：
- **合入 sit 之前**发现的问题（到货检查、到货编译失败）：在原 `task/*` 分支上修。
- **合入 sit 之后**发现的问题（sit CI、真机测试）：写 bug 单，开 `fix/*` 分支修，**不回原任务分支**。

## 1. 规划：拆任务 + 画关系图

1. 新建批次关系图 `graphs/<批次>.md`（格式见第 8 节），把需求拆成任务节点，分配层级。
2. 每个任务按 `tasks/TEMPLATE.md` 写文档，头部必须写全：批次、层级、组、硬依赖、软依赖、同层并行关系、**冲突域**（会改的文件/目录）。
3. 规划自检（全部满足才能派发）：
   - **同层无硬依赖**：同一层的任务之间不能有硬依赖；有的话，把被依赖的一方提到上一层。
   - **同层冲突域不相交**：同一层任务改的文件不能重叠。共享追加点除外（见下文），但要在图里标出来。
   - **软依赖要有契约**：软依赖（只需要对方的接口，不需要对方的代码）必须在双方的文档里写明约定的签名或文件名，并写清缺失时的占位做法，例如 `// TODO(Txx)`。
   - **并发上限**：同时运行的 Codex 不超过 8 个。超过的话，按关键路径（后面挂的任务最多的）优先派发。
4. 共享追加点（多个任务可以同时追加、合并时两边都保留）：`R/values*/strings_<短名>.xml`（各建各的文件）、`CodegClient.kt` 的 region、`MainShell.kt` 的路由表（每个任务只追加一个 `composable`）。其余文件一律视为独占。

## 2. 派发

1. 先同步 sit：`git checkout sit && git merge main`（main 有热修复或文档更新时），然后推送 sit。
2. 主仓库 `E:\claude\codeg-android` 保持 checkout 在 `sit`（codeg-cli 的 worktree 基于主仓库 HEAD 创建）。在本层任务全部派出之前，不要切换分支。
3. 用派发脚本按层派发。把关系图里的节点状态改成 🔄，并记录 run ID。
4. **就绪即派**：默认按层推进。但某个节点的所有硬依赖都已经 🔗 合入 sit、并且 sit CI 是绿的，就可以提前派发，不必等同层其他任务。

## 3. 到货检查（每个任务交付时，逐个做，不等同层其他任务）

1. 读 Codex 报告和测试文档，按模板检查有没有缺项。
2. **范围检查**：`git diff --name-only sit...origin/task/Txx` 与任务文档的冲突域对比，有越界就打回，或者由协调方回退那部分改动。
3. **到货编译**：在后台对 `task/Txx` 触发 verify，Codex 不等结果。
   - 通过 → 状态改为 📦，进入集成。
   - 失败 → 小问题（import、类型、可见性）由协调方直接在 `task/Txx` 上修；大问题把日志发回原任务返工。修好再触发一次，直到通过。

## 4. 集成到 sit

1. 按层级顺序合入，同层内按到货顺序：`git merge --no-ff -m "Merge task/Txx" origin/task/Txx`。
2. 冲突处理：code-index 取 ours；`CodegClient.kt` 的 region 冲突两边都保留（`union_regions.py`）；字符串文件本来就不会冲突；其他冲突说明冲突域规划有漏洞，要记进关系图的"复盘"。
3. 合完一层后：在 Windows 端运行 `python -X utf8 scripts/gen_code_index.py` → 提交 → 推送 sit → 触发 sit verify。
4. **层级门禁**：sit CI 变绿，本层的节点才能标 🔗，下一层才能派发。CI 失败 → 进入第 6 步（bug 单编号 `Bnn`，类型写"编译"）。

## 5. 测试

1. 默认在**批次末尾**统一做真机测试（只编译一次 APK）。如果某一层有用户可见的大改动，可以在层末加一轮测试，并在关系图里标注。
2. 把 sit 最新的 debug APK 装到手机上（`install.sh`），按各任务测试文档的用例逐条执行，操作一律用 `safe.sh`。
3. 结果记在 `tests/RESULTS-<批次>.md`，表格列为：用例编号 | 结果（✅/❌/⚠️跳过+原因）| bug 单号 | 截图路径。
4. 失败的用例 → 写 bug 单，进入第 6 步。

## 6. 修复（bug → 新的修复任务）

1. **写 bug 单** `bugs/Bnn-<区域>.md`（按模板写）：来源（用例编号或 CI run）、复现步骤、预期结果、实际结果、日志或截图、定位到的文件、归属的原任务。
2. **按冲突域分组**：同一区域（同一个目录划分，例如 sessions / projects / settings / misc / designsystem）在同一轮里的所有 bug 合并成一个修复任务，避免多个修复分支改同一个文件。不同区域的修复任务并行。
3. **编译类问题优先、单独处理**：sit 编译不过会阻塞所有测试，所以由协调方直接开 `fix/Bnn-build` 修。改动很小时不派 Codex。
4. **派发修复任务**：先 `git checkout sit && git pull`，再按 bug 单派发。修复任务使用 **CI 模式**：改动小、基于 sit，跑一轮 verify 就能确认在集成环境下可以编译。分支名 `fix/Bnn-<区域>`，提交信息写 `Fixes Bnn (Txx)`。
5. **合回 sit 并复测**：复测 bug 单对应的用例 + 该区域的回归点，结果补进 RESULTS。通过后 bug 单状态改为 ✅，否则继续下一轮。
6. 第 5、6 步循环，直到 RESULTS 里没有 ❌。

## 7. 发布

1. 全量回归：对 sit 最终版本再跑一次所有用例里标了"回归"的条目，加上明暗主题抽查。
2. 合入 main：`git checkout main && git merge --no-ff sit -m "Release <批次>"` → push main，触发 auto-release。
3. 在真机上验证自动更新（横幅 → 下载 → 覆盖安装，数据保留）。
4. 收尾：把关系图节点全部改成 ✅，写"复盘"小节（冲突、返工原因、规划漏洞）；主仓库保持在 sit，进入下一批次。

## 8. 关系图格式（思维导图式缩进树）

```
批次 <名称>：<目标>　集成分支：sit　状态：<进行中/已发布>
│
├─ L1 <层名>　[并行 ×N｜同层无依赖]　门禁：sit CI 绿
│  ├─ 组 A <组名>　⟂ 组内互不依赖
│  │  ├─ T01 <标题>　<状态>　← 硬依赖：无　冲突域：<文件/目录>
│  │  └─ T02 <标题>　<状态>　← 硬依赖：无　冲突域：…
│  └─ 组 B …
│
├─ L2 <层名>　[并行 ×N]　门禁：L1 全部 🔗
│  ├─ T03 <标题>　← 硬：T01　软：T02（契约：<签名/文件>）　冲突域：…
│  └─ T04 …
│
├─ SIT 集成测试
│  ├─ S1 编译门禁（协调方）
│  ├─ S2 真机测试 → RESULTS-<批次>.md
│  └─ S3 修复轮次：B01 <区域> …（按区域并行）→ 回到 S2 复测
│
└─ 发布：sit → main
```

- 状态图例：⏳ 待写文档　📝 文档就绪　🔄 开发中　📦 已交付（到货检查与编译通过）　🔗 已合入 sit　✅ 测试通过　❌ 有 bug（附 Bnn）
- 依赖类型：
  - **硬依赖 ←**：需要对方的代码已合入 sit。决定节点放在哪一层。
  - **软依赖 ⇠**：只需要对方的接口约定，可以同层并行。必须写契约和占位做法。
  - **⟂**：组内互不依赖。
- **同层内不允许硬依赖**。如果出现了，就把被依赖的一方上移一层，或者把两个任务拆开、合并重组。
- 关系图是唯一事实来源：派发、到货、合入、测试、修复时都要同步更新状态。
